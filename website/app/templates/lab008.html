How Do We Threat-Model an AI Agent?

The model is only one component. Agent risk emerges across identity, authority, instructions, memory, tools, delegation, execution, evidence, and control — and it keeps changing through drift, public-model exposure, infrastructure reach, and the evidence we can actually verify.

The model is not the whole system

Model-only view asks

  • What did the model generate?
  • Was the response accurate?
  • Could the prompt be manipulated?

System threat model asks

  • Who is acting?
  • Under which authority?
  • Which instructions and memory influenced the decision?
  • Which tools, data, delegates, and execution paths are reachable?
  • Which controls and evidence surround the action?

Threats change across the agent lifecycle

The same agent presents different assets, trust boundaries, and failure modes at each stage. Controls and evidence have to follow it.

  1. 1. Registration and identity

    Assets
    Agent identity record, credentials, owner and principal binding.
    Trust boundaries
    Enrollment process to identity provider; agent to session.
    Failure modes
    Impersonation, unmanaged or shadow agents, stale or shared credentials.
    Controls
    Managed registration, credential binding, owner attestation.
    Evidence
    Registry entries, issuance logs, session-binding records.

  2. 2. Delegation and authorization

    Assets
    Grants, scopes, approvals, validity windows.
    Trust boundaries
    Principal to agent; agent to sub-agent or worker.
    Failure modes
    Excessive scope, replayed approvals, authority that outlives its purpose.
    Controls
    Narrowing at each handoff, purpose binding, live re-evaluation.
    Evidence
    Grant lineage, policy decisions, approval-to-target bindings.

  3. 3. Instruction and context assembly

    Assets
    Approved task, system instructions, assembled context.
    Trust boundaries
    Trusted instructions versus retrieved, user, or third-party content.
    Failure modes
    Prompt injection, instruction replacement, context poisoning.
    Controls
    Instruction and data separation, provenance labels, context filtering.
    Evidence
    Context assembly traces, retrieval source records, blocked-override logs.

  4. 4. Planning and tool selection

    Assets
    Plan, objective, tool catalog, data selection.
    Trust boundaries
    Agent reasoning to tool and data authorization.
    Failure modes
    Objective drift, alternate tool after denial, data beyond stated purpose.
    Controls
    Intent-level binding across tools, purpose and sensitivity limits, escalation triggers.
    Evidence
    Plan and tool-call records, denial-and-retry correlation.

  5. 5. Execution and coordination

    Assets
    Runtimes, queues, delegates, network paths, resource budgets.
    Trust boundaries
    Agent runtime to internal services, public models, and the network.
    Failure modes
    Queued work after expiry, fan-out, cost amplification, unapproved egress.
    Controls
    Egress allow-lists, per-agent budgets, queue and credential scoping.
    Evidence
    Network, queue, and billing telemetry from outside the agent.

  6. 6. Learning, memory and adaptation

    Assets
    Persistent memory, learned preferences, adapted behavior.
    Trust boundaries
    Session to persistent store; earlier sessions to later privileged tasks.
    Failure modes
    Poisoned memory, unreviewed learning, stale context steering later actions.
    Controls
    Memory provenance, promotion review, quarantine and expiry.
    Evidence
    Memory write and read logs, behavior baselines, change history.

  7. 7. Monitoring and evidence

    Assets
    Telemetry, receipts, audit records, detection rules.
    Trust boundaries
    Agent self-report versus independent observation.
    Failure modes
    Self-report treated as proof, gaps between systems, undetected drift.
    Controls
    Independent telemetry, cross-system correlation, drift detection.
    Evidence
    Verifiable receipts, coverage reports, documented evidence gaps.

  8. 8. Revocation, containment and recovery

    Assets
    Revocation channel, control plane, recovery procedures.
    Trust boundaries
    Enforcement outside the agent; recovery back into normal operation.
    Failure modes
    Stop recorded but not enforced, surviving credentials or delegates, unsafe restoration.
    Controls
    External containment, credential revocation, staged recovery.
    Evidence
    Independent confirmation that each path is closed and state is clean.

Example agent-system architecture

A useful threat model starts with the whole operating system around the model: the principal, identity and authority plane, runtime, instructions, memory, tools, delegates, queues, network reach, public-model boundaries, protected data, independent evidence, and external containment.

Seven threat surfaces

A threat case has one primary surface and may include secondary surfaces.

Identity

Agent and principal identity, session binding, and impersonation paths.

Authority

Delegated grants, approvals, scope, and validity windows.

Instructions and intent

Approved task definitions versus untrusted instruction channels.

Memory and context

Retrieved content and persistent memory across sessions.

Tools and execution

Tool endpoints, data purpose, queues, and runtime paths.

Delegation and coordination

Workers, child agents, and handoff boundaries.

Evidence and control

Independent telemetry, recovery, and residual-risk confidence.

Four cross-cutting risk dimensions

Surfaces say where a threat sits. Dimensions describe risks that cut across several surfaces and change over time. A case can carry any number of them.

Behavior and usage drift

Objective drift, scope creep, retries, and use of valid authority for unapproved purposes. This is not the same as model-weight drift.

Learning and memory drift

Poisoned memory, unsafe adaptation, stale context, and unreviewed learning. Memory or context updates are not model retraining.

External model exposure

Public-model calls, unapproved endpoints, retention, training reuse, and model or provider supply-chain exposure. Approved governed endpoints differ from uncontrolled public-model use.

Network and resource impact

Lateral movement, egress, cost amplification, queues, and credential reach. Availability or cost impact is related to, but distinct from, security compromise.

Keep these distinctions visible

  • Behavioral drift is not model-weight drift. An agent can keep the same model weights and still drift by changing how it uses approved authority, tools, or objectives.
  • Memory or context updates are not model retraining. Writing to persistent memory, retrieval stores, or preference history can change later privileged behavior without any weight update.
  • Approved external-model use is not uncontrolled public-model exposure. A contracted, governed endpoint with known retention differs from sending sensitive context to an unapproved public model or provider.
  • Model and provider supply-chain exposure matters. Where prompts and data go—training reuse, retention, subprocessors, and endpoint provenance—is part of the threat model, not an afterthought.
  • Attempted control is not independently verified control. A stop, revoke, or filter claim needs evidence outside the agent’s self-report.

Teaching notes

  • The model is only one part of the agentic system.
  • Threat modeling begins with assets and trust boundaries, and it must be repeated across the agent lifecycle.
  • Tool permission does not equal authorization for every purpose or data set.
  • Retrieved content and persistent memory are separate trust boundaries.
  • Delegation can expand the threat surface.
  • Drift is not a policy violation at any single moment. Behavior and usage drift happens inside valid identity and authority, so it needs purpose binding and trend detection, not only allow or deny checks. That is distinct from model-weight drift.
  • Learning and memory drift is not usage drift, and it is not retraining. Usage drift reuses authority for a new purpose; learning drift changes what the agent believes or prefers through memory or context updates, and can influence later tasks even when each action looks permitted.
  • Approved external-model use is not public-model exposure. A contracted, governed endpoint with known retention differs from sending sensitive context to an uncontrolled public model, including retention, training reuse, and supply-chain exposure at the provider.
  • Network and resource impact is a separate question from data exposure. Valid credentials can still cause lateral movement, queue growth, and cost amplification without a single sensitive record leaving.
  • Controls require independent evidence; an agent self-report is not verification.
  • Complete control coverage does not mean zero risk.
  • This prototype does not replace a production security review.

The next control question

A threat model tells us what could go wrong. The next challenge is determining how continuously we can detect when the system begins to move away from its approved identity, authority, purpose, behavior and operating boundary.
